# PokerALL — архитектура

Статус: **утверждено владельцем**. Этот файл — основа проекта; любые изменения архитектуры вносятся сюда.

---

## 0. Как ведётся работа

- Владелец работает только с Android-телефона, компьютера нет. Весь код пишется в облачных сессиях Claude Code и пушится в GitHub.
- Каждый шаг — отдельная ветка `feat/*` и pull request. Владелец проверяет результат на телефоне и мёржит.
- Проверка результата:
  - **Веб-превью.** `expo export --platform web`, затем `scripts/build-preview.mjs` собирает одну самодостаточную HTML-страницу (бандл и шрифты внутри). Она публикуется как приватный артефакт claude.ai и открывается в браузере телефона. Используется после каждого шага.
  - **APK.** Workflow `android-apk` собирает настоящий Android APK и прикладывает его к релизу `preview-<ветка>` (pre-release). Запуск: коммит с `[apk]` в сообщении, вручную из вкладки Actions (когда workflow есть в main) или тег `v*`. Нужен для проверки того, что не видно в браузере: вибрации, производительности, системной кнопки «назад».
- Облачная сессия, в которой пишется код, может не иметь доступа к npm. Тогда зависимости ставит CI: workflow `ci` обновляет `pnpm-lock.yaml` и публикует архив `node_modules` в релиз `deps-<хэш lockfile>`, а `scripts/fetch-deps.sh` скачивает его в сессию. После этого typecheck, lint, веб-сборка и скриншоты (Playwright) работают локально.
  - **Тесты.** Вся логика (движок, оценщик рук, рейтинг) проверяется автоматическими тестами в CI на каждом пуше.

## 2. Отличия от брифа

| В брифе | Решение | Почему |
|---|---|---|
| react-native-skia | react-native-svg + Reanimated | Стол, карты и матрица 13×13 одинаково работают на Android и в веб-превью. Skia в браузере требует загрузки CanvasKit на несколько мегабайт. Skia можно добавить точечно, если понадобятся тяжёлые эффекты. |
| Fastify или NestJS | Fastify | Меньше шаблонного кода и «магии», проще поддерживать одному владельцу. |
| react-native-iap или RevenueCat | Решение на этапе v1 | RevenueCat не поддерживает RuStore. Вероятный вариант — собственная серверная валидация для обоих магазинов за общим `PaymentProvider`. |

Остальной стек — как в `CLAUDE.md`.

## 3. Визуальный стиль «Neon»

- Тёмная тема по умолчанию: фон `#07070D`, поверхности `#11111C` / `#1A1A2A`.
- Неоновые акценты: циан `#00F0FF` (основной, действия игрока), маджента `#FF2BD6` (агрессия, рейз, рейтинг), лайм `#B6FF3B` (выигрыш, правильный ответ), янтарь `#FFC23D` (Pro, награды).
- Текст: `#EDEDF7`, второстепенный `#8A8AA3`.
- Свечение — через SVG-фильтры и многослойные тени, дозированно: только на активных элементах (твой ход, кнопки действия, выигрыш банка), чтобы стол оставался читаемым.
- Светлая тема «Daylight»: те же оттенки, приглушённые и затемнённые для контраста.
- Шрифты: Unbounded для заголовков, Inter для текста, моноширинные (tabular) цифры для стеков и банков. Оба шрифта с кириллицей (Space Grotesk из первой версии плана кириллицы не имеет).
- Карты: обычная и четырёхцветная колода; масть всегда различается формой значка, а не только цветом.
- Игровые элементы: XP-бар, стрики, всплывающие награды, анимация раздачи и сбора банка; всё отключаемо в настройках.
- Цветовые токены живут в одном файле темы, ни одного «сырого» цвета в компонентах.

## 4. poker-engine

### Карты
Карта — целое число `0..51`: `rank * 4 + suit`, где `rank` 0 = двойка … 12 = туз, масти `c d h s`. Помощники для строк вида `As`, `Td`.

### Оценщик рук
- Оценка 5–7 карт, результат — целое число (больше = сильнее) и категория комбинации.
- Алгоритм на битовых масках по мастям: проверка флеша, стрит по таблице из 8192 масок, пары/сеты/каре по счётчикам рангов. Без больших таблиц, достаточно быстро для Monte Carlo на телефоне.
- Тест: полный перебор всех 2 598 960 пятикарточных рук со сверкой с известным распределением категорий; отдельный «медленный» тест для 7-карточных рук.

### Машина состояний раздачи
```ts
startHand(table: TableState, rng: Rng): { state: HandState; events: EngineEvent[] }
legalActions(state: HandState, seat: number): LegalActions
  // fold | check | call(amount) | bet{min,max} | raise{min,max}
applyAction(state: HandState, action: PlayerAction): { state: HandState; events: EngineEvent[] }
```
- Чистые функции, неизменяемое состояние. Каждый переход порождает события — одни и те же события используются для анимаций, истории раздачи и сетевого протокола.
- Правила: блайнды и анте; в heads-up баттон ставит малый блайнд и ходит первым префлоп; минимальный рейз = размер последнего полного рейза; неполный all-in-рейз не переоткрывает торговлю; возврат неуравненной ставки; сайд-поты считаются по вкладам в конце раздачи; нечётная фишка — первому месту слева от баттона; автоматическое открытие борда при all-in.
- `Rng` внедряется снаружи: офлайн — сидируемый генератор (воспроизводимые раздачи для реплеера и тестов), на сервере — криптостойкий.

### История раздачи
Каноничный JSON: конфигурация, места, `seedHash`, действия, борд, результат. Из него строятся реплеер, статистика (VPIP, PFR и т. д.) и позже экспорт в текст.

### Эквити
Monte Carlo и точный перебор, когда комбинаций меньше ~2 млн. Считается порциями с уступкой потока UI (на Android) и в Web Worker (в веб-превью), интерфейс не блокируется.

### Боты
- Профиль бота: целевые VPIP/PFR, агрессия, частота блефа, вероятность ошибки.
- Префлоп: диапазоны из `content` (TAG — эталонные, LAG и loose-passive — расширенные и смещённые).
- Постфлоп: быстрый Monte Carlo эквити против предполагаемого диапазона соперника + pot odds + текстура борда для решения о ставке, колле или блефе.
- Сложность = вероятность ошибки + точность оценки эквити.
- Боты работают на устройстве в казуальной офлайн-игре и на сервере для заполнения казуальных столов. В рейтинговых матчах ботов нет никогда.

## 5. content

### Диапазоны
Не зависят от языка. Нотация с весами, совместимая с популярными покерными программами:
```json
{
  "id": "6max-100bb-rfi-CO",
  "format": "6max",
  "stackBb": 100,
  "spot": { "type": "RFI", "hero": "CO" },
  "actions": {
    "raise": { "sizeBb": 2.3, "range": "22+, A2s+, K8s+, Q9s+, J9s+, T9s, 98s, 87s, ATo+, KJo+, A9o:0.5" }
  },
  "level": "beginner",
  "free": true,
  "source": "simplified-educational"
}
```
Всё, что не попало ни в одно действие, — фолд. `A9o:0.5` означает 50%.

### Уроки
```
packages/content/lessons/<lessonId>/meta.json   уровень, трек, free/pro, порядок блоков
packages/content/lessons/<lessonId>/en.json     тексты
packages/content/lessons/<lessonId>/ru.json
```
Типы блоков: `text` (markdown), `handRanking`, `tableDiagram` (подсветка позиций), `rangeMatrix` (ссылка на диапазон по id), `cards`, `potOddsCalc`, `quiz`. Тексты — в файлах локалей, диапазоны — по id.

### Глоссарий
`glossary/en.json` и `glossary/ru.json` с общими id терминов.

### Проверки в CI
Zod-схемы для всех файлов контента; тест, что у каждого урока и термина есть обе локали и все ключи; тест, что каждая нотация диапазона корректно парсится.

## 6. Мобильное приложение

- Навигация (expo-router), четыре вкладки: **Играть**, **Академия**, **Тренировка**, **Профиль**. Рейтинговые режимы — внутри «Играть».
- Состояние: Zustand. Локальное хранение: AsyncStorage за обёрткой `src/lib/storage.ts` (на вебе это localStorage). Если понадобится скорость, обёртку можно переключить на MMKV в одном месте.
- Офлайн-прогресс: у каждой записи `updatedAt`; с v1 синхронизируется с сервером.
- Строки интерфейса: `apps/mobile/src/locales/en.json`, `ru.json`; `scripts/check-locales.mjs` в CI проверяет одинаковые ключи и плейсхолдеры.
- Подготовка к targetSdk 36: edge-to-edge и predictive back закладываются с первого шага.

## 7. Сервер (v1)

- Fastify: REST для авторизации, профиля, синхронизации прогресса, лидербордов, покупок. Socket.IO: очередь матчмейкинга и столы.
- Каждый стол или матч — актор в памяти одного процесса, владеющий своим состоянием. Снимок состояния пишется в Redis после каждого действия для восстановления после падения. Масштабирование позже — маршрутизация по `tableId`.
- Авторизация: короткий access-JWT (15 мин) + refresh-токен (30 дней, ротация, хранится в БД в виде хэша). Google ID token проверяется на сервере. Пароли — argon2. Гостевой аккаунт привязан к устройству и может быть привязан к Google/email.
- Тасовка: случайный seed из `crypto.randomBytes` на каждую раздачу, колода — Fisher–Yates на детерминированном генераторе от seed. `seedHash = sha256(seed)` отправляется в начале раздачи, seed раскрывается в конце; клиент может проверить порядок колоды.

## 8. Протокол событий (Socket.IO, v1)

Все сообщения типизированы в `packages/shared` и проверяются zod-схемами.

Клиент → сервер:
| Событие | Данные |
|---|---|
| `queue:join` | `{ mode: 'ranked_hu' \| 'ranked_6max' \| 'casual_cash' \| 'casual_sng' }` |
| `queue:leave` | — |
| `table:action` | `{ handId, seq, action: { type, amount? } }` |
| `table:chat` | `{ text \| reactionId }` |
| `session:resume` | `{ tableId }` |

Сервер → клиент:
| Событие | Данные |
|---|---|
| `queue:status` | позиция, окно рейтинга, время ожидания |
| `match:found` | `{ matchId, tableId, mode }` |
| `table:snapshot` | полное состояние стола, персонально для получателя (свои карты видны, чужие нет) |
| `hand:start` | `{ handId, seedHash, button, stacks, blinds }` |
| `hand:holeCards` | только своему игроку |
| `hand:action` | публичное действие игрока |
| `hand:street` | `{ street, board }` |
| `hand:turn` | `{ seat, deadline, legalActions }` |
| `hand:showdown` | открытые руки и комбинации |
| `hand:end` | `{ seed, pots, winners }` |
| `match:end` | `{ places, ratingDelta }` |

- Действие клиента содержит `handId` и ожидаемый `seq`; устаревшие и повторные действия сервер отклоняет (идемпотентность).
- При переподключении сервер присылает `table:snapshot`, клиент восстанавливает стол без потери места.

## 9. Схема БД (Prisma, v1–v2)

- **User**, **AuthIdentity** (google, email, guest-device), **RefreshToken**, **UserSettings**, **AgeConfirmation**.
- **ChipWallet** и **ChipLedger** (только казуальные фишки). Причины начисления — enum: `starting_bank`, `daily_bonus`, `streak`, `academy_reward`, `rebuy_timer`, `invite_reward`, `casual_win`, `casual_loss`. Типов «перевод между игроками» и «покупка» нет в схеме вообще.

- **Match** (mode, season, status, startedAt, endedAt); **MatchParticipant** (place, ratingBefore, ratingAfter, abandoned).
- **Hand** (match или казуальный стол, history JSON, seedHash, seed); **HandParticipant** (флаги для статистики: vpip, pfr, threeBet, cbet, wtsd, wsd и т. д.).
- **LessonProgress**, **TrainerAttempt**, **SrsCard** (интервальное повторение), **DailyChallengeResult**.
- **Entitlement** (pro, источник, expiresAt), **StorePurchase** (магазин, токен, статус, сырые данные проверки).
- **CosmeticItem**, **UserCosmetic** (источник: покупка или сезонная награда).
- **Friendship**, **Club**, **ClubMember**.
- **Report**, **ModerationAction**, **AnticheatFlag**.

## 10. Рейтинг (v1)

- **Heads-up — Glicko-2.** Старт: 1500 / RD 350 / волатильность 0.06. Обновление после каждого матча. Отображаемый рейтинг = `rating − 2·RD`.
- **6-max — OpenSkill (Plackett–Luce)** по занятому месту. Отображаемый рейтинг = `μ − 3σ`.
- Отдельная лестница рангов для каждого режима. Пороги Bronze…Master настраиваются по реальному распределению; Grandmaster — топ-500 режима.
- Калибровка: первые 10 матчей без ранга.
- Мягкий сброс сезона: `rating = 1500 + 0.5 · (rating − 1500)`, RD поднимается до минимума 150.
- Матчмейкинг: окно ±100, расширяется на 50 каждые 10 секунд до ±400, дальше — честный статус ожидания.
- Выход из матча = последнее место + запрет на поиск 5 / 15 / 60 минут по нарастающей.

## 11. Подписка и честная игра (v1)

- Право `pro` хранится на сервере. Клиент кэширует подписанный токен права с ограниченным сроком, обновляет его раз в сутки; без сети Pro работает до 3 дней.
- Пока у игрока идёт рейтинговый матч, сервер помечает его `inRankedMatch`, клиент блокирует Pro-инструменты, а серверные Pro-функции отказывают.
- Честно о пределах: блокировку на клиенте можно обойти на взломанном устройстве, а помощником можно пользоваться и на втором телефоне. Поэтому основная защита — поведенческий античит: тайминги, точность решений относительно базовой стратегии, аномальная статистика пар игроков.

## 12. CI/CD

- `ci.yml`: установка, проверка типов, линтер, проверка локалей, веб-сборка — на каждый пуш в `main`, `feat/**`, `fix/**`. Если `package.json` изменился, коммитит обновлённый `pnpm-lock.yaml` и публикует архив зависимостей. При падении последние строки лога попадают в аннотацию check-run (их можно прочитать через REST API).
- `android-apk.yml`: `expo prebuild` + Gradle собирают release APK (arm64-v8a и armeabi-v7a) и кладут его в pre-release `preview-<ветка>` или в релиз версии для тега `v*`.
- Пока тестовые APK подписаны debug-ключом React Native. Перед публикацией в Google Play: сгенерировать upload-ключ, хранить его в GitHub Secrets (и резервную копию у владельца), включить Play App Signing.
